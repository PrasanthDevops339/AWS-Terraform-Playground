# CloudTrail Cost Spike — Root Cause Analysis & Remediation

> **Incident Period:** February 5–6, 2026 (recurring on subsequent ECS runs)
> **Affected Component:** `config_aggregator.py` ECS Task — every scheduled run, worst case 12-hour run on Feb 5–6
> **Cost Drivers:** `USE2-PaidEventsRecorded` + `USE2-InsightsEvents` (Management Events + Anomaly Detection)

---

## 1. What Happened

CloudTrail costs increased by approximately **600%** beginning February 5–6, 2026, with a **recurring elevated pattern on subsequent scheduled ECS runs**. Cost Explorer confirms two dominant drivers:

- `USE2-PaidEventsRecorded` — management events beyond the free first-copy baseline
- `USE2-InsightsEvents` — CloudTrail Insights anomaly detection events, charged separately when unusual API call rates are detected

### Cost Explorer Pattern (Feb 1–17)

| Period | Approx Relative Cost | Spike Drivers |
|---|---|---|
| Feb 1–3 | Baseline (~50–100) | Normal |
| **Feb 5–6** | **Peak (~1,300–1,400)** | `PaidEventsRecorded` + `InsightsEvents` — 12-hour ECS run |
| Feb 7–9 | Elevated (~300–450) | `PaidEventsRecorded` — subsequent ECS runs |
| Feb 9–10 | Near baseline | — |
| **Feb 11–13** | **High (~700–800)** | `PaidEventsRecorded` + `InsightsEvents` — further ECS runs |
| Feb 14–16 | Near baseline | — |
| Feb 17 | Slightly elevated | Next scheduled run |

The environment runs two active trails:

| Trail | Scope |
|---|---|
| `aws-controltower-BaselineCloudTrail` | Org-wide, Multi-Region |
| `aws-aft-CustomizationsCloudTrail` | Org-wide, Multi-Region |

The spike was **not** caused by trail creation or a Config rule deployment. The Feb 5–6 worst-case spike was triggered by the ECS task running for ~12 hours. However, the **recurring elevated pattern on other days confirms the root cause is active on every normal scheduled run** — the 12-hour outlier simply made it catastrophic on Feb 5–6.

### The `USE2-InsightsEvents` Cost Component

CloudTrail Insights monitors API call rates and charges for events when it detects abnormal volume. Its appearance prominently on Feb 5 and Feb 11–13 means two things:

1. The API call volume generated by the ECS task was **high enough to trigger CloudTrail's own anomaly detection**.
2. You are being charged for **both** the underlying management events and the Insights detection events on top — a compounding cost effect.

Disabling CloudTrail Insights on one or both trails (if not required for compliance) would eliminate this secondary cost driver entirely.

## 2. Why It Happened — Root Causes

### Root Cause 1: `check_account()` Called Per Resource Without Caching (Highest Impact)

In `config_aggregator.py`, the function `check_account()` queries DynamoDB on **every non-compliant resource iteration**:

```python
# Line 428 — called inside the per-resource loop
is_one_dot_zero = check_account(account_name)
```

`check_account()` runs a `dynamodb:Query` API call each time. There is **no caching** on this function, unlike `get_account_name_cached()` which has an `account_cache` dict.

Every DynamoDB `Query` is a **management event** recorded to CloudTrail. If the aggregator processes 5,000 non-compliant resources across 50 accounts, this fires **5,000 DynamoDB Query calls** per run instead of 50.

| Scenario | DynamoDB Calls per Run |
|---|---|
| Before fix (no cache) | 1 per resource (thousands) |
| After fix (cached by account) | 1 per unique account (50–100) |

---

### Root Cause 2: `get_rule_description()` — Paginated Config API Calls Per Rule × Account × Region

```python
# Called inside per-resource, per-rule inner loop
annotation = get_rule_description(rule.get('configRuleName'), account_id, region, rule_ann)
```

The cache key is `(rule_name, account_id, region)`. Every unique combination triggers a `GetAggregateComplianceDetailsByConfigRule` paginator call, which may issue **multiple API pages** per cache miss.

At scale, with 20 rules × 100 accounts × 5 regions, this can produce **10,000+ Config API calls** per run, each a paid management event.

---

### Root Cause 3: ECS Task Ran for ~12 Hours — Runtime Multiplier on All Uncached Calls

The `config_aggregator.py` ECS task ran for approximately **12 continuous hours** on Feb 5–6 instead of completing in its expected shorter window. This is the primary trigger for the cost spike.

Because `check_account()` fires one uncached `dynamodb:Query` per resource and `get_rule_description()` fires paginated Config API calls per rule × account × region, the total management event count scales **linearly with task runtime**. A 12-hour run vs. a 1-hour run produces roughly 12× the API call volume — directly explaining the ~600% spike.

**Why the task ran for 12 hours** requires further investigation. Likely causes:

- A much larger non-compliant resource result set than typical (larger pagination loop)
- API throttling causing the built-in retry/sleep loop to stall (`ThrottlingException` → `time.sleep(3 * tries)` up to 3 retries per call)
- `get_rule_description()` paginating over an unexpectedly large annotation result set per rule
- No task-level timeout or ECS `stopTimeout` configured, allowing the container to run indefinitely

**Recommended investigation:** Check ECS task logs for the Feb 5–6 run to identify where time was spent — whether in the Config query loop, the `get_rule_description()` paginator, or blocked on throttle retries.

---

### Root Cause 4: boto3 Clients Created Inside Hot-Path Loops (Contributing Factor)

```python
# get_rule_description() — line 195 — new client on every cache miss
client = boto3.client('config', region_name=REGION, ...)

# S3 upload loop — line 492 — new client per account group
s3 = boto3.client('s3', region_name=REGION)
```

Repeated client creation inside loops can trigger `sts:AssumeRole` or `sts:GetSessionToken` calls if role chaining is in use. These are management events. Even without role chaining, it adds unnecessary overhead on each iteration.

---

### Root Cause 5: CloudTrail Insights Enabled — Charges Compound on High-Volume Runs

`USE2-InsightsEvents` is visible as a significant cost component on Feb 5 and Feb 11–13 in Cost Explorer. CloudTrail Insights charges per 100,000 events analyzed when it detects unusual API activity.

The high management event volume from the uncached ECS runs triggered Insights on multiple occasions. This creates a **compounding cost structure**: every run that exceeds the normal API call threshold gets charged twice — once for `PaidEventsRecorded` and again for `InsightsEvents` analysis on top.

## 4. Remediation

### Fix 1 — Add Cache to `check_account()` ✅ IMPLEMENTED

**Status: Applied to `config_aggregator.py` on Feb 17, 2026.**

`version_cache` dict and `check_account_cached()` wrapper were added at lines 252–260, following the same pattern as the existing `account_cache` / `get_account_name_cached()`. The call site at line 428 was updated to use the cached wrapper. The original `check_account()` function is unchanged.

```python
# Lines 252–260 — added to config_aggregator.py
# A cache to store 1.0/2.0 version lookups once they've been fetched per account
version_cache = {}

def check_account_cached(account_name):
    # Returns cached result to avoid repeated DynamoDB queries for the same account
    if account_name not in version_cache:
        version_cache[account_name] = check_account(account_name)
    return version_cache[account_name]
```

```python
# Line 428 — updated call site
# Before
is_one_dot_zero = check_account(account_name)

# After (applied)
is_one_dot_zero = check_account_cached(account_name)
```

**Reduction achieved:** DynamoDB `Query` calls drop from 1 per resource to 1 per unique account name per run. Typically a 50–200x reduction depending on resource density per account.

---

### Fix 2 — Move boto3 Clients Outside Loops

Create clients once at module level or before the loop begins, not inside functions or per-iteration:

```python
# Before — inside get_rule_description() on every cache miss
client = boto3.client('config', region_name=REGION, config=Config(retries={'max_attempts': 10}))

# Before — inside S3 upload loop on every account group
s3 = boto3.client('s3', region_name=REGION)
```

Move both to module-level constants or initialize once before the relevant loop starts.

---

### Fix 3 — Validate Trail Overlap Configuration

Check both active trails to ensure management events are not being recorded twice (first copy is free, second copy is paid):

```
aws cloudtrail get-trail --name aws-controltower-BaselineCloudTrail
aws cloudtrail get-trail --name aws-aft-CustomizationsCloudTrail
```

Verify:
- Are both trails set to Read + Write management events?
- Are both Multi-Region?
- Do both have Organization trail scope?

If yes on all three for both trails — **both are recording the same events**, and the second copy is fully paid. Consider scoping one trail to Write-only or disabling management event recording on one trail if operational requirements allow.

### Fix 4 — Add ECS Task-Level Timeout and Alerting

The 12-hour runtime was the core multiplier. Without a task timeout, the container ran indefinitely. Two controls prevent recurrence:

**A. Set an ECS task `stopTimeout` and a hard runtime limit:**

In the ECS task definition or Fargate scheduled task, configure a maximum runtime so the task is forcibly stopped if it exceeds expectations:

```json
{
  "containerDefinitions": [{
    "stopTimeout": 120
  }]
}
```

For scheduled tasks triggered via EventBridge, add a CloudWatch alarm on ECS task `RunningTaskCount` duration — alert if a task is still running after N minutes past its expected completion window.

**B. Set a script-level watchdog timeout:**

Add a timeout guard inside `config_aggregator.py` using Python's `signal` module or a start-time check at the top of the main loop:

```python
import signal

def _timeout_handler(signum, frame):
    logger.error("Task exceeded maximum allowed runtime. Exiting.")
    raise SystemExit(1)

# Allow max 2 hours before hard exit
signal.signal(signal.SIGALRM, _timeout_handler)
signal.alarm(7200)
```

### Fix 5 — Investigate Why the Feb 5–6 Run Lasted 12 Hours

Query CloudTrail logs to confirm which API calls dominated the Feb 5–6 window and identify where the task was spending time:

```sql
-- Athena query against CloudTrail S3 logs
SELECT
    useridentity.arn,
    eventsource,
    eventname,
    COUNT(*) AS event_count
FROM cloudtrail_logs
WHERE
    eventtime >= '2026-02-05T00:00:00Z'
    AND eventtime <= '2026-02-06T23:59:59Z'
GROUP BY useridentity.arn, eventsource, eventname
ORDER BY event_count DESC
LIMIT 50;
```

Cross-reference with ECS task logs (CloudWatch Logs) to identify whether the delay was in:
- The Config aggregator query pagination loop (large result set)
- `get_rule_description()` paginator stalling on a specific rule/account/region
- Repeated `ThrottlingException` retries with `time.sleep()` backoff

### Fix 6 — Review CloudTrail Insights Configuration

`USE2-InsightsEvents` appeared prominently on Feb 5 and Feb 11–13, meaning Insights is enabled on at least one trail and is triggering on the elevated API call volumes. Insights charges $0.35 per 100,000 events analyzed.

**Evaluate whether Insights is required:**

```bash
# Check which trails have Insights enabled
aws cloudtrail get-insight-selectors --trail-name aws-controltower-BaselineCloudTrail
aws cloudtrail get-insight-selectors --trail-name aws-aft-CustomizationsCloudTrail
```

If Insights is enabled for `ApiCallRateInsight` and there is no active operational or compliance requirement for it, disabling it will immediately eliminate the `InsightsEvents` cost component on future runs.

**If Insights must remain enabled:** fix the underlying API call volume first (Fix 2 — cache `check_account()`). Once the call volume normalizes, the Insights anomaly threshold will no longer be crossed and `InsightsEvents` charges will stop appearing.

## 5. Future View — Considerations for Deploying New Config Rules

Deploying Config rules into a large organization aggregator requires a controlled approach to avoid cost and compliance noise spikes. The following practices should be applied to all future rule deployments.

### 5.1 Stage Deployments by OU or Account Tier

Never deploy a new Config rule org-wide simultaneously. Use a phased rollout:

| Phase | Scope | Purpose |
|---|---|---|
| Phase 1 | Sandbox / Dev OU (1–5 accounts) | Validate rule logic and evaluation behavior |
| Phase 2 | Non-production OUs (10–20 accounts) | Validate at scale, observe event volume |
| Phase 3 | Production OUs | Full deployment with known event baseline |

Each phase should run for **at least one full aggregator evaluation cycle** before expanding.

---

### 5.2 Pre-Deployment: Estimate Resource Scope

Before deploying, estimate the number of in-scope resources to anticipate evaluation volume:

```sql
-- AWS Config Advanced Query to count resources in scope
SELECT
    resourceType,
    COUNT(*) AS resource_count
FROM aws_config_configuration_snapshot
WHERE resourceType = 'AWS::EC2::Volume'
GROUP BY resourceType;
```

A rule targeting `AWS::EC2::Volume` across 200 accounts with an average of 300 volumes = **60,000 `PutEvaluations` calls** on first deployment. Each call is a management event.

---

### 5.3 Use `MaximumExecutionFrequency` to Control Evaluation Rate

For periodic rules (not change-triggered), set the maximum execution frequency to reduce ongoing event volume:

| Frequency | Use Case |
|---|---|
| `One_Hour` | High-sensitivity security rules |
| `Three_Hours` | Standard compliance rules |
| `Six_Hours` | Low-urgency inventory rules |
| `TwentyFour_Hours` | Cost-optimization or tagging rules |

Avoid defaulting to `One_Hour` for all rules — every evaluation cycle generates management events across all in-scope accounts.

---

### 5.4 Set Change-Triggered Scope Narrowly

For change-triggered rules, explicitly define the `Scope` to the minimum required resource types. Broad or undefined scope means **any resource change** can trigger evaluation:

```hcl
# Terraform — narrow scope to only EBS volumes
resource "aws_config_config_rule" "ebs_encryption" {
  name = "ebs-volume-encryption"

  scope {
    compliance_resource_types = ["AWS::EC2::Volume"]
  }

  source {
    owner             = "AWS"
    source_identifier = "ENCRYPTED_VOLUMES"
  }
}
```

---

### 5.5 Monitor CloudTrail Costs Before and After Each Rule Deployment

Establish a cost baseline check as part of the Config rule deployment runbook:

1. Record `USE2-PaidEventsRecorded` daily cost from Cost Explorer **3 days before** deployment.
2. Deploy the rule to Phase 1 scope.
3. Monitor `USE2-PaidEventsRecorded` for **24–48 hours** after deployment.
4. If cost increases by more than 20%, investigate before proceeding to Phase 2.

---

### 5.6 Separate Remediation Automation from Config Evaluation

If a Config rule triggers automated remediation (e.g., SSM Automation, Lambda), each remediation action generates its own management events. A rule that remediates 1,000 resources on first deployment = 1,000 additional API calls on top of the evaluation events.

Decouple remediation from initial deployment:
- Deploy rule in **Audit mode** (report-only) first.
- Review non-compliant resource count.
- Enable remediation in a separate, controlled step with rate limiting.
